# 6. CI

## O que é

Integração contínua, aqui, é um workflow do GitHub Actions que roda num runner Ubuntu limpo, sem o seu Docker Desktop e sem o seu cluster. Ele prova que o repositório ainda constrói. Entrega contínua, neste desenho, não é o runner aplicando YAML em produção. É o runner publicando um artefato imutável e gravando a referência desse artefato no Git. O Argo CD faz a entrega.

Os dois workflows ainda não executaram: este clone não tem remote. Eles passam a rodar quando o repositório estiver no GitHub.

## ci.yml

Dispara em todo `push` e todo `pull_request`. `permissions: contents: read`. Dois jobs.

**validate**

- `terraform fmt -check` e `terraform validate` com `init -backend=false` (não baixa provider de estado remoto; não há backend remoto)
- `kustomize build` de `dev` e de `prod`, saída no kubeconform 0.6.7, schema do Kubernetes 1.32, `-strict`
- `docker build` de `apps/referencia`, tag `prumo-referencia:ci`, sem push
- Trivy (`aquasecurity/trivy-action` 0.28.0) nessa tag. Falha o job se houver CVE `CRITICAL` ou `HIGH` com correção já publicada (`ignore-unfixed: true`, `exit-code: 1`). Varre OS e bibliotecas.

**kind**, depois do validate

Sobe um kind com o mesmo `kindest/node:v1.32.2` (`azure/setup-helm` não entra nesse job de cluster; o kind-action v1.12.0 cria o cluster). Instala cert-manager e Kyverno, aplica as políticas, espera o webhook e aplica [policies/fixtures/pod-invalido.yaml](../../policies/fixtures/pod-invalido.yaml). O apply tem de falhar. Se o Pod for aceito, o job falha. Em seguida aplica o overlay `dev`, espera o rollout e faz port-forward até `/healthz` responder. Esse kind é destruído com o runner. Ele não é o cluster do `make up`.

## release.yml

Só dispara em `push` na `main` quando muda `apps/referencia/**` ou o próprio workflow. Permissões: `contents: write` e `packages: write`.

1. Calcula `ghcr.io/<repositório em minúsculas>:<GITHUB_SHA>`. A tag é o SHA do commit, não `latest`. A política do Kyverno recusaria `latest` nos namespaces do workload.
2. Faz login no GHCR com `GITHUB_TOKEN` e dá push da imagem.
3. Na pasta da base, `kustomize edit set image` troca a tag em `deploy/referencia/base/kustomization.yaml`.
4. Commita só esse arquivo e dá push. A mensagem cita o SHA.

O commit da tag não altera `apps/referencia/`, então o `paths` do workflow não dispara de novo. O Argo CD, no cluster que aponta para esse Git, vê o `kustomization.yaml` novo e puxa a imagem. O runner não tem kubeconfig de produção e não roda `kubectl`.

Enquanto o cluster local usa `prumo-referencia:local` carregada pelo `kind load`, um cluster que não tem essa carga precisa da tag do GHCR e de `imagePullPolicy` que permita o pull. A troca é o bloco `images` da base, não um patch por ambiente: `dev` e `prod` sobem o mesmo artefato.
