# 6. CI

CI constrói. CD entrega. São trabalhos diferentes, e misturar os dois é o que faz um pipeline dar `kubectl apply` num cluster de produção a partir de um runner.

O workflow [ci.yml](../../.github/workflows/ci.yml) roda em todo push e pull request:

- `terraform fmt` e `terraform validate`
- `kustomize build` dos dois overlays, conferido pelo kubeconform
- build da imagem e scan com o Trivy
- um kind limpo, no runner, instala cert-manager e Kyverno, recusa o Pod de [policies/fixtures/pod-invalido.yaml](../../policies/fixtures/pod-invalido.yaml) e sobe o overlay `dev` até o `/healthz` responder

O workflow [release.yml](../../.github/workflows/release.yml) só roda quando `apps/referencia/` muda na branch `main`. Ele publica a imagem no GHCR e grava a tag nova em `deploy/referencia/base/kustomization.yaml`. Esse commit não altera `apps/referencia/`, então o workflow não dispara de novo.

O Argo CD vê o commit da tag e reconcilia. O runner não aplica o overlay de produção.
