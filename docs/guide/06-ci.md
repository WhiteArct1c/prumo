# 6. CI

## What it is

Continuous integration, here, is a GitHub Actions workflow that runs on a clean Ubuntu runner, without your Docker Desktop and without your cluster. It proves the repository still builds. Continuous delivery, in this design, is not the runner applying YAML to a live cluster. It is the runner publishing an immutable artifact and writing that artifact's reference into Git. Argo CD does the delivery.

The workflow only runs when this repository is on GitHub. A local clone does not need it: `make up` builds the image and loads it into the node.

## ci.yml

It fires on `push` and `pull_request`, except when the only changes are `README.md`, `docs/`, `LICENSE`, or `keys/`. `permissions: contents: read` on the whole workflow. Only the `release` job asks for more. Three jobs, in sequence: `validate`, `kind`, and `release`.

Off `main`, a new push cancels the previous run of the same branch. On `main` it does not cancel, because a `release` cut in the middle would leave the image on GHCR without the tag in Git.

**validate**

- zizmor 1.31.1 on the workflows and Dependabot. Fails an unpinned action, a persisted checkout credential, template injection, and dangerous triggers such as `pull_request_target`
- `terraform fmt -check` and `terraform validate` with `init -backend=false` (does not download a remote-state provider; there is no remote backend)
- `kustomize build` of `dev` and `prod`, and of `platform/apps/lite`, `platform/apps/full`, `platform/observability/lite`, and `platform/observability/full`, output through kubeconform 0.6.7, Kubernetes 1.32 schema, `-strict`
- `docker build` of `apps/prumo`, tag `prumo:ci`, no push
- Trivy (`aquasecurity/trivy-action` v0.35.0) on that tag. Fails the job if there is a `CRITICAL` or `HIGH` CVE that already has a published fix (`ignore-unfixed: true`, `exit-code: 1`). Scans OS and libraries.

**kind**, after validate

Brings up a kind cluster with the same `kindest/node:v1.32.2` (the kind-action v1.12.0 creates the cluster). Installs cert-manager and Kyverno, applies the policies, waits for the webhook, and applies [policies/fixtures/invalid-pod.yaml](../../policies/fixtures/invalid-pod.yaml). The apply must fail. If the Pod is accepted, the job fails.

Then it builds the image with the name the `dev` overlay asks for (`prumo:local` before the first release, `ghcr.io/...:<tag>` after) and loads it into kind. The test runs the code from this commit, not the image from the previous release. It applies the overlay, waits for the rollout, and port-forwards until `/healthz` answers. That kind cluster dies with the runner. It is not the `make up` cluster.

**release**, after `validate` and `kind`

Only runs on `push` to `main`. Permissions: `contents: write` and `packages: write`. Because it depends on the two previous jobs, an image that fails Trivy or does not come up on kind never reaches GHCR.

1. The tag is the content hash of `apps/prumo` (`git rev-parse HEAD:apps/prumo`), not `latest`. The Kyverno policy would reject `latest` in the workload namespaces.
2. If `deploy/prumo/base/kustomization.yaml` already has that tag, the job stops here. That is what happens on a push that only touches docs or manifests.
3. Logs in to GHCR with `GITHUB_TOKEN` and pushes `ghcr.io/<repository in lowercase>:<tag>`.
4. In the base directory, `kustomize edit set image` writes the new tag.
5. Commits only that file, `pull --rebase` if `main` moved, and pushes.

A commit made with `GITHUB_TOKEN` does not fire another run, so there is no loop. If a run fails in the middle, the next push to `main` sees that the tag is still missing from Git and publishes again. The runner has no production kubeconfig and does not run `kubectl`.

## After a release

The base starts asking for `ghcr.io/<owner>/prumo:<tag>`. The swap is the `images` block on the base, not a per-environment patch: `dev` and `prod` run the same artifact.

`make up` still builds that tag from this tree and loads it into the node, so a clone does not need the GHCR package. `imagePullPolicy: IfNotPresent` only asks a registry when the image is missing from the node.

Argo CD reads the git daemon that serves the local clone, so a tag that only exists on the remote reaches the cluster after it is in this clone ([ADR 0006](../adr/0006-argocd-reads-local-git.md)).

## Actions pinned by SHA

Every action is pinned to a commit SHA, with the version in a comment. An action tag is mutable: in March 2026, whoever took over `aquasecurity/trivy-action` rewrote the old tags to code that read the runner secrets. A SHA does not change. [Dependabot](../../.github/dependabot.yml) opens a monthly PR with the new SHAs, only for versions published at least 7 days ago. A compromised release is usually found before that.

The same rule applies to what is not an action. kustomize and kubeconform downloaded with `curl` go through `sha256sum -c` against the hash published on the release, and the zizmor image is referenced by digest.

No checkout keeps the token in `.git/config` (`persist-credentials: false`). `release` needs the token for the push, so it enters only on the last step, as an environment variable. The GHCR login receives the same token, because that is what it is for. What changes is that the token does not sit in the cloned repository, where any later step would read it.

The rest of the model is in [security](../security.md).
